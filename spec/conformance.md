# Conformance — the vector corpus and the sample suite

Two test assets pin the contract between the compiler and any lmcode runtime:

1. **The conformance corpus** (`lmcode-cpp/conformance/`): language-neutral bytecode vectors with
   expectation files, generated by the compiler. Any runtime that loads DSLB v6 runs them.
2. **The sample suite** (`lmcode-cpp/sample-suite/`): an end-to-end integration corpus for the
   canonical "shop" sample hosts (`lmcode-*-sample` ports). It pins whole-program behavior: exact
   stdout bytes, exit codes, and the CLI protocol.

Normative sources:

- Generator and acceptance test: `lmscript/scripts/generate-dsl-conformance.ts` and
  `lmscript/tests/dsl-conformance.test.ts` (C01) in the lmscript mono tree.
- Runner and vector sets: `lmcode-cpp/conformance/` (`run.cpp`, `compile-vectors.py`, `vectors/`,
  `stdlib-vectors/`).
- Sample suite: `lmcode-cpp/sample-suite/` (`CONTRACT.md`, `README.md`, `manifest.json`,
  `run-suite.py`, `run-suite.sh`, `run-suite.lms`, `compile.py`, `check-compile-errors.py`).
- Requirement numbers (R26, R33, R34, R49, …) are from
  `lmscript/durable-memory/requirements/dsl-bytecode.md`.

## The core corpus (`conformance/vectors/`)

The current C++ checkout at `lmcode-cpp` revision `aaa9088a542d43daf81aefb9b024fbb971825f3f`
contains 406 vectors, manifest format `dsl-conformance/3`, `bytecode_version` 6. Each vector is three files:
`NAME.dsl` (the DSL body source), `NAME.dslb` (the bytecode), `NAME.expect` (the expectation).
The directory also holds `schema.json` (the conformance schema), `schema-extra.json` (the same
schema plus one function the stub does not implement, for the unbound-import case),
`schema-ctx.json` (context `t` retyped, for the context-type case) and `manifest.json`.

The compiler-side C01 baseline at compiler source `aa6fecb5` contains 82 vectors (including nine return vectors); the
expanded canonical runtime corpus above adds 324 boundary/rejection cases. Use the
generator revision matching the selected manifest: the historical 82-vector generator
does not reproduce the expanded 406-vector corpus.

The vectors are generated, not hand-written: `generate-dsl-conformance.ts` compiles each
`NAME.dsl` with the real compiler (`compileDsl` in `lmscript/dsl.ts`) against the conformance
schema and writes the bytes. Run it as:

```sh
node --experimental-strip-types scripts/generate-dsl-conformance.ts OUT_DIR
```

Generation is deterministic: regenerating the set produces byte-identical `.dslb` files (C01
generates twice into separate directories and deep-compares every vector). Vectors that must be
malformed (all `load_error` vectors, the empty-line-table runtime case) are produced by mutating
valid compiler output after emission — never hand-assembled — and carry `"mutated": true` in the
manifest.

The manifest describes the host stub every runtime implements (`manifest.host`): context `t` is a
`Trace` that records lines (`int N`, `float %.15g`, `str S`, `bool true|false`, `thing ID`),
context `root` is a `Thing` with id 0, context `xs` is an `IntList` of `[0, 1, 2, 3]`, and the
host functions (`bound`, `thing`, `var`, `twice`, `half`, `fail`, `yes`) follow their schema
names. `conformance/run.cpp` is the reference implementation of that stub.

### The `.expect` protocols

Line 1 of every `.expect` is the kind. Payload lines follow. Literal `\n` (backslash-n) inside a
payload line encodes a newline in the expected text. Line grammars:

- `trace` — each payload line is one expected trace line, in order, after a successful run of the
  body. A line starting with `~ ` is an approximate match for platform-libm results: the text up
  to the last space must match exactly, and the final token is a finite number compared with
  tolerance `1e-12 * max(|expected|, 1e-300)`.
- `runtime_error` — one payload line, a substring of the error message. The load must succeed and
  the run must fail.
- `runtime_error_at` — four payload lines: error code (e.g. `RUN_ERROR`, `RUN_HOST`), line,
  column, message substring. Line/column are the located error's source position (S5); `0` means
  "no location attached".
- `load_error` — one payload line, a substring of the load error. `load()` must throw; nothing
  runs.
- `entries` — one payload line per rule entry, in source order: `NAME ANNOTATION INTERFACE`, where
  INTERFACE is the canonical `interface NAME(T1, ...) -> R` text. The body is not run.
  `entries-empty` (an empty table, `u16 0`) has no payload lines.
- `call` — line 2 is `ENTRY ARGS-JSON` (entry name, one space, then a JSON array of arguments);
  line 3 is the result line `result int N | result float X | result string S | result bool
  true|false | result thing ID | result void`; the remaining lines are the expected trace. An enum
  result is its constant name as `result string NAME`; an object result is `result thing ID`
  (the fixture Thing's id). Numeric arguments take their types from the entry's parameter types;
  a JSON object `{"type": "Thing", "id": N}` constructs the conformance Thing handle. Every
  call-kind vector runs the body once before the entry call, and the trace covers both (there is
  no per-vector switch; `call-body-trace` proves it).
- `call_error` — line 2 is `ENTRY ARGS-JSON`, line 3 is the error code, line 4 a message
  substring. A wrong argument count fails with RUN_HOST `call entry 'NAME' expects N argument(s);
  found M` before any execution.
- `call_error_at` — line 2 is `ENTRY ARGS-JSON`, then code, line, column, message substring, as in
  `runtime_error_at`.

### Return sink and frame expectations

The nine return vectors are part of the 406-vector C++ corpus and carry a trailing `sink` record.
The record is not a trace line: the runner removes it before interpreting payload lines and compares
both fields after execution, including the partial sink payload after a failure. The
manifest carries the same object in `expect.sink`. Its form is `sink {"json":STRING,"frame":STRING}`, with JSON string
escaping applied to both values. The `json` field is the invocation-owned `ResultSink` payload;
`frame` is the exact LF-delimited `LMCODE_RETURN_BEGIN`, payload, `LMCODE_RETURN_END` text (or the
empty string when execution fails). A host binds and resets one sink before the body, keeps it through
selected entry calls, and emits the frame only after dispatch and application validation. A sink
trailer must never be counted as a trace line or silently ignored. The separate
`conformance/return-vectors/` gate has 9 fixtures and is run by `make conformance`; its `vectors.lock`
pins schema, sources, bytecode and expected bytes. This return gate covers slices 1, 2 (in progress),
3, 5 and 8; block execution and `load_schema` (slice 4) are landed in mono main at `0bc80277` (2026-10-31); they are absent from the released 0.2.444 compiler, and execution additionally needs a host that emits the terminal frame (the C++ SDK main does — verified end to end against `0bc80277` in the wp40 review; the samples do not yet, slice 6), and are
covered by the mono execution/frame tests rather than certified by this VM-only corpus.

### What C01 pins

`tests/dsl-conformance.test.ts` ("DSL C01") at compiler source `aa6fecb5` is the 82-vector compiler-side gate. It regenerates the corpus
and asserts:

- exactly 82 generated vectors in the compiler-side C01 set (including 9 return vectors), manifest
  format `dsl-conformance/3`, `bytecode_version` equal to the
  compiler's `DSL_VERSION` (6);
- every vector's `.expect` line 1 is a known kind and agrees with the manifest's expectation key;
  minimum kind counts (trace ≥ 9, entries ≥ 1, call ≥ 8, call_error ≥ 1, call_error_at ≥ 1,
  runtime_error ≥ 3, load_error ≥ 8);
- no vector carries a `run_body` flag — every `call*` vector runs the body first, always;
- every non-mutated `.dslb` starts with `DSLB` and version 6; the four JSON files are exactly
  `manifest.json`, `schema.json`, `schema-extra.json`, `schema-ctx.json`;
- every code region (body and each entry) decodes exactly with the known instruction widths, ends
  with HALT, and has a sorted line table whose pcs stay inside the code;
- the entries section ends the file exactly (no trailing bytes); entry metadata constants resolve;
  entry interface text matches `^interface NAME(...) -> `; parameter locals are unhidden;
- `entries` expectations list every entry in the file, in order, and `call*` vectors name an entry
  that exists in the file;
- every opcode from 0x01 to 0x36 appears in at least one vector;
- the whole set is deterministic across two runs.

A companion test ("DSL C02") pins the mutated empty-line-table vector byte-for-byte against a
fresh compile: only the body line records are removed and the v6 entry tail survives.

C01 is a runtime handoff contract: it validates deterministic generation and wire structure, not
native execution. Execution conformance is the runtime's job, via `run.cpp` or a port of it.

### The stdlib catalog vectors (`conformance/stdlib-vectors/`)

268 vectors, manifest format `dsl-conformance/2`, `bytecode_version` 6. Each is again
`NAME.dsl` / `NAME.dslb` / `NAME.expect`; the bytecode is compiled, not hand-assembled, and the
expectations are independently specified (never regenerated from VM output). Groups by schema:

| Schema | Vectors | Covers |
|--------|---------|--------|
| `schema.json` (string catalog) | 18 | all 16 string functions plus repeat failure cases |
| `math.schema.json` | 11 | all 16 integer/float math overloads; wrapping powers, exact floor roots near i64 limits, signed zero, NaN, halfway-away rounding |
| `collections.schema.json` | 32 | list/map methods, mutation chaining, insertion order, raw-byte keys, NaN lookup, arena limit; plus the explicitly registered testing catalog (`print`, `assert_close`) |
| `file.schema.json` | 16 | file IO with a per-vector temp directory (`test_temp_dir`), CR bytes, a 1,200,000-byte write, long/unicode paths (`test_long_path`) |
| `data.schema.json` | 112 | the v2 data catalog (containers/Json), positive and negative contract |
| `v3.schema.json` | 38 | std v3 byte codecs and map snapshots |
| `fuzz.schema.json` | 41 | seeded property corpus (seeds 7, 42, 20261024; `scripts/gen-std-corpus.py` derives expectations from Python oracles) |

Two additional expectation kinds appear here (the runner `run.cpp` implements them):

- `runtime_error_exact` — two payload lines: the error code, then the complete message after
  removing only the SDK's `dsl line N:C: ` source prefix. Pins exact collection bounds, missing-key
  and assertion messages.
- `runtime_error_file` — three payload lines: `RUN_HOST`, the function name, and the path relative
  to `test_temp_dir()` (empty = the directory itself). The actual error must begin with
  `FUNCTION: ABSOLUTE_PATH: ` and end with a nonempty OS reason, keeping the check portable while
  allowing localized diagnostics.

`bytes(hex)` supplies raw-byte fixtures and `t.hex(value)` records lowercase hex, so invalid
UTF-8, NUL and partial slices are compared as bytes, not text.

Recompiling after a language change:

```sh
python3 conformance/compile-vectors.py conformance/stdlib-vectors   # or conformance/vectors
```

`compile-vectors.py` recompiles every unmutated vector with `LMSCRIPT_BIN` (default `lmscript`),
placing exactly one wrapper line before the body so source-located errors refer to body line + 1.
It never rewrites `.expect` files.

### Running the corpus (C++ reference)

```sh
make conformance          # builds build/conformance, runs both directories
build/conformance conformance/vectors
build/conformance conformance/stdlib-vectors
```

The runner prints `ok - NAME (kind)` per vector and `PASS n/n vectors`; exit 0 on success.
`LMCODE_TRACE=1` dumps per-vector trace/error records for differential comparison
(`scripts/diff-stdlib.py` builds all runners and byte-compares those records). A conforming port
implements the same stub and runs the same directories; the requirement is byte-level agreement
with the `.expect` semantics above, not with C++ internals.

## The sample suite (`sample-suite/`)

114 pinned cases, manifest format 1, `bytecode_version` 6, schema `sample.dsl.json` (schema 2
with merged default std; the domain-only declarations are in `host.schema.json`), and
`compiler_minimum` `0.2.420`. The suite is the source of truth shared by all `lmcode-*-sample`
host ports. Case distribution by expected exit: 77 × 0, 36 × 3 (host load/run failure), 1 × 4
(application failure).

Each manifest case declares `name`, `bytecode` + `bytecode_sha256`, `expected_exit`,
`features`, and usually `source` + `source_sha256` and `timeout_seconds` (default 30). The runner
refuses a manifest whose hashes do not match the committed files, so sources, bytecode and
expectations change only together. Expected output lives in `expected/NAME.out` (exact stdout
bytes) and `expected/NAME.exit`; expectations are recorded with `record.py` and reviewed — never
regenerated by a passing run. The binary fixtures under `fixtures` (`invalid.bin`,
`zero-bytes.bin`, `chunk.bin`) are hex-encoded in the manifest and materialized into a fresh
`SAMPLE_TMP` per case.

### Dispatch rules (`CONTRACT.md`)

The host runs each case in a fresh process against contexts `shop` and `ledger`:

- Money is signed int64 cents; `money(int)`/`shop.price(int)` take cents, their float overloads
  take units and round half away from zero. Integer money operations wrap modulo 2^64.
- Trace lines come from `print`; then exactly one JSON result line plus LF:
  `{"ok": true, "result": {"balance": 0, "entries": 0, "note": "", "entries_called": 0}}`.
- Rule entries (R47–R49): after the body runs, the host enumerates the program's entries in
  source order, calls every `@item` entry once per shop item with the item's Money handle, calls
  every `@total` entry once with `shop.total()`, and never calls entries with other annotations.
  A non-void entry result is printed as `entry NAME = VALUE`; the result object reports
  `"entries_called": N` (0 for programs without rules).
- Negative final ledger balance is an application failure after VM success:
  `{"ok": false, "phase": "app", "code": "APP_FAIL", "message": "ledger: negative balance"}`,
  exit 4.
- Canonical load messages: LOAD_BAD_BYTECODE → `invalid sample bytecode`, LOAD_SCHEMA_MISMATCH →
  `sample schema mismatch`, LOAD_UNBOUND → `sample import mismatch`. VM/host run errors retain the
  SDK message, including the `dsl line N:C: ` prefix.
- CLI: `--version` prints `lmcode-cpp-sample 0.2.0` (other ports use their own binary name);
  `--dsl-schema [--json]` prints the exact schema bytes; `--dsl-signatures` prints sorted
  canonical signatures; `--dsl FILE` runs a case; usage errors exit 2 with phase `cli`, code
  `CLI_USAGE`.

### Mutation and compile-error pins

- `090-bad-bytecode` — `001-literals` with byte 0 flipped; `expected_exit` 3.
- `091-schema-mismatch` — `001-literals` with byte 6 (inside the schema hash) flipped; exit 3.
- `092-wrong-handle-import` — the import `fn host_echo_money(Money) -> Money` rewritten to
  `fn host_echo_money(Items) -> Money`; a declared-but-wrong handle type is LOAD_UNBOUND at load
  (a loader cannot know a callback's future dynamic return), exit 3.
- `093-v5-refused` — `001-literals` re-tagged with `bytecode_version` 5; every current runtime
  refuses it (`unsupported bytecode version 5 ...`), exit 3.
- `compile-errors/` — sources that the compiler must reject with exit 2:
  `recursive-inline.lms` (recursive inline functions are a compile error; there is no recursive
  bytecode call stack), `rule-annotation-without-implements.lms`, `rule-method-mismatch.lms`.
  `check-compile-errors.py` verifies them before any case runs.

Some cases declare `compiler_features` (`lmcode-literals-v1` for the 2xx literal cases,
`lmcode-rule-methods-v1` for 067, `lmcode-rule-entries-v1` for 068/069): source reproduction with
a compiler that lacks the feature is an explicit error, not a silent skip. The whole corpus is
DSLB v6, first reproduced byte-for-byte by `@lmctl-ai/lmctl` 0.2.444; 0.2.442/0.2.443 accept the
rule syntax but still write v5.

### Running the suite

Against one sample host binary (argv array, fresh `SAMPLE_TMP` and fixtures per case, exact stdout
bytes + exit code compared, stderr must be empty):

```sh
./sample-suite/run-suite.sh /path/to/lmcode-cpp-sample          # lmscript driver
python3 sample-suite/run-suite.py /path/to/lmcode-cpp-sample    # equivalent Python driver
```

`run-suite.py` first validates the manifest hashes, then `check-compile-errors.py` (compiler
rejection), then `protocol.py` (the host's declared signatures are derived independently from the
schema, so a missing or extra registration fails even if no program calls it), then runs every
case. `protocol.py` and the CLI discovery checks are part of the contract: a port that only runs
the bytecode cases is not conforming.

Useful companions: `compile.py` recompiles all programs (`--output DIR` reproduces without
touching the committed manifest; `--exclude-feature` gives a partial reproduction check);
`check-recompile.py` verifies hashes before reproducing; `audit.py` fails if any canonical std
signature in the schema is uncovered by the corpus's import tables. The cross-port matrix
(`run-all-samples.sh --all`) builds and runs every port and compares byte outputs against both the
expectations and the other ports; missing ports are FAIL, not SKIP.
