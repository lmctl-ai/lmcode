# CI and local verification

Pushes to main and pull requests run the suite on GitHub-hosted runners. No
self-hosted machine or globally installed lmctl is required. CI downloads
@lmctl-ai/lmctl with Node 24 into a fresh temporary npm prefix.

The compiler selector is the manual workflow input compiler_version, then the
repository variable LMCODE_COMPILER_VERSION, then scripts/ci/compiler-version
(currently 0.2.456, including the required dry invocation marker). To test a newer release or tag,
run the ci workflow manually and set compiler_version, for example staging.
The historical 0.2.450 producer omits the mandatory dry marker and cannot be
paired with current hosts. The selected baseline must support that contract.
No fallback to retired flags is attempted. A compiler that cannot satisfy the suite fails visibly; planned language
features must not be claimed as passing through skipped checks.

Run from the repository root with Node 24, npm, Git and Python 3 (Unix example;
on Windows activate the venv through Scripts/activate). Existing reference clones
can be supplied through LMCODE_CPP/LMCODE_LMOK instead of cloning again:

```sh
git clone https://github.com/lmctl-ai/lmcode-cpp scripts/ci/work/cpp
git clone https://github.com/lmctl-ai/lmok scripts/ci/work/lmok
git clone https://github.com/lmctl-ai/lmcode-cpp-sample scripts/ci/work/sample
git clone https://github.com/lmctl-ai/lmcode-js scripts/ci/work/js
make -C scripts/ci/work/sample all
python3 -m venv scripts/ci/work/python
source scripts/ci/work/python/bin/activate
python -m pip install -r scripts/ci/requirements.txt
source scripts/ci/install-compiler.sh
export LMCODE_CPP="$PWD/scripts/ci/work/cpp"
export LMCODE_LMOK="$PWD/scripts/ci/work/lmok"
export LMCODE_SAMPLE="$PWD/scripts/ci/work/sample"
export LMCODE_JS="$PWD/scripts/ci/work/js"
bash scripts/ci/run-suite.sh
```

To select a different published compiler:

```sh
COMPILER_VERSION=staging source scripts/ci/install-compiler.sh
bash scripts/ci/run-suite.sh
```

The cross-runtime workflow resolves a selected npm tag once to an exact version
and snapshots main revisions of six runtime repos,
the five separate matching sample repos (JavaScript bundles its sample), and lmcode-cpp's reference vectors before starting
its 30 native jobs (Linux x64/arm64, macOS x64/arm64, Windows x64). It runs runtime
tests, sends the same reference core/stdlib vectors to each runner, refreshes
samples with their own sync scripts, and recompiles/runs their sample suites.
Go uses a local module replacement in the disposable sample checkout so it
exercises the selected runtime revision. Refreshed lockfiles stay in the
disposable checkout; nothing is committed or pushed upstream.
The vectors and sample suite remain in lmcode-cpp; this workflow does not move
the canonical source or silently skip catalog incompatibilities.

For a single cross-runtime run after installing the compiler, supply disposable
checkouts and the language name (cpp, rust, go, java, csharp or js):

```sh
LANGUAGE=cpp RUNTIME_DIR=/path/to/lmcode-cpp \
REFERENCE_CPP_DIR=/path/to/reference-lmcode-cpp \
SAMPLE_DIR=/path/to/lmcode-cpp-sample bash scripts/ci/cross-runtime.sh
```

The [executable v6 example](examples/v6.lms) and its adjacent schema
are compiled in CI, including a deliberately mistyped variant that must fail.
This tests the published compile-only form, not the planned block-return syntax.
The generated file must carry the lmcode bytecode (DSLB v6) header; a v5-output control also fails.

CI also extracts and compiles the seven current code examples in
[the language reference](../../spec/language.md), with an explicit declaration schema
for the illustrated host domain. The keyword inventory is data, not a test.
A corrupted return-type control proves that changes to the document are checked.
These are compile-only checks; the native sample matrix verifies host execution.

The grammar corpus checker takes explicit reference roots and refuses missing,
empty or body-free corpora. Lark is installed only in the CI/private Python
environment. The standard inventory is regenerated by its own generator and
checked against current C++ schema/docs; drift remains a hard failure. Current
compiler-source return-write syntax is checked by the grammar, separately from
the published 0.2.444 compiler examples. This does not certify end-to-end
ResultSink/sample adoption; the cross-runtime sample audit exposes that gap.

Manual runs use a separate concurrency group, so main edits do not cancel an
explicit compiler-version experiment or a snapshot verification already in progress.

The tutorial runner extracts its 15 programs and compares the documented stdout,
exit codes, compile diagnostics and a corrupted schema-hash example against the
built C++ sample. Only paths and the explicitly abbreviated scope-name inventory
are normalized. A changed expected-output control must fail.

JavaScript cells use Node24 on all five platforms. They generate the dependency-free
SDK lock in the disposable runtime checkout, run npm ci, sync std and all four
vector families from the snapshotted reference using the SDK sync scripts, then
run unit/mutation/full conformance gates. The bundled sample is refreshed with
sync-sample-suite.mjs and checked with npm run verify:pins and npm run sample-suite.
SAMPLE_DIR is the runtime checkout for js; there is no lmcode-js-sample repository.
No failed npm/conformance command is caught or converted to a successful cell.

The [JavaScript guide](../../guides/javascript-host.md) is qualified by
check-js-guide.py in the same ordinary documentation suite: its labeled schema,
ESM host and lmcode program execute through the compiler and SDK, with exact
stdout/exit/stderr checks. A changed expected result, a broken host callback and
an extra unclassified example each fail. Set LMCODE_JS to a local JS checkout.
The tutorial checker explicitly discovers its host into a temporary schema cache
before --check; it never uses or populates the operator's schema cache.

Current qualification requires the standalone compiler contract: no retired
preflight-bypass option, explicit discovery for cold CLI schemas, and compiler-library
fixture generation in maintainer tooling. Runtime/sample entrypoints and their
canonical SDK/suite pins are repaired in their owning repositories; the matrix
runs them without argument-stripping compatibility shims or skipped checks.
